۲. مفهوم تگ و رابطه آن با مقاله

تگ برای دسته‌بندی موضوعی مقاله‌ها استفاده می‌شود. برای مثال، یک مقاله ممکن است هم‌زمان تگ‌های TypeScript، JavaScript و Backend داشته باشد.

رابطه مقاله و تگ از نوع چندبه‌چند یا Many-to-Many است؛ یعنی هر مقاله می‌تواند چند تگ داشته باشد و هر تگ هم می‌تواند به چند مقاله متصل شود.

موجودیت Tag

فایل موجودیت تگ:

articles-backend/src/modules/tags/entities/tag.entity.ts

بخش رابطه در موجودیت تگ به این شکل است:

@ManyToMany(() => Article, (article) => article.tags)
articles!: Article[];

موجودیت Article

در موجودیت مقاله، رابطه معکوس تعریف شده است:

@ManyToMany(() => Tag, (tag) => tag.articles)
@JoinTable({ name: "article_tags" })
tags!: Tag[];

جدول واسط article_tags شناسه مقاله و شناسه تگ را به یکدیگر متصل می‌کند.

ستون معنا
articlesId شناسه مقاله
tagsId شناسه تگ
نکته کلیدی: وقتی از ManyToMany استفاده می‌کنیم، TypeORM رابطه را از طریق جدول واسط مدیریت می‌کند. لازم نیست برای هر تگ یک ستون جداگانه در جدول مقالات بسازیم.

۳. پذیرش tagIds در DTO

برای ارسال شناسه تگ‌ها از طریق API، فیلد tagIds به DTOهای ساخت و ویرایش مقاله اضافه شد.

فایل:

articles-backend/src/modules/articles/articles.dto.ts
export interface CreateArticleDto {
  title: string;
  slug: string;
  content: ArticleContent;
  status?: "draft" | "published";
  tagIds?: number[];
}

export interface UpdateArticleDto {
  title?: string;
  slug?: string;
  content?: ArticleContent;
  status?: "draft" | "published";
  tagIds?: number[];
}

چرا tagIds آرایه است؟

چون مقاله می‌تواند چند تگ داشته باشد، شناسه تگ‌ها را در قالب آرایه ارسال می‌کنیم. برای مثال: 

{
  "tagIds": [1, 2, 3]
}

این مقدار به معنای انتخاب تگ‌های دارای شناسه‌های ۱، ۲ و ۳ است. اینترفیس TypeScript به‌تنهایی ورودی HTTP را اعتبارسنجی نمی‌کند؛ برای همین از Zod نیز استفاده می‌کنیم.

۴. علت اصلی کارنکردن tagIds هنگام ساخت مقاله

در ابتدا درخواست ساخت مقاله شامل tagIds بود، اما سرویس مقدار خالی دریافت می‌کرد.

دلیل خطا چه بود؟

در فایل کنترلر، createArticleSchema فیلد tagIds را تعریف نکرده بود.

Zod به‌صورت پیش‌فرض کلیدهای ناشناخته را از خروجی یک شیء معمولی حذف می‌کند. بنابراین وقتی این کد اجرا می‌شد: 

const data = createArticleSchema.parse(req.body);

مقدار tagIds که در اسکیما تعریف نشده بود، از خروجی اعتبارسنجی حذف می‌شد.

اصلاح انجام‌شده

tagIds: z.array(z.number().int().positive()).optional(),

این فیلد باید داخل z.object({...}) در اسکیما ساخت مقاله قرار داشته باشد.

نتیجه: پس از پذیرش tagIds در اسکیما، سرویس می‌تواند شناسه‌ها را دریافت کند و رابطه مقاله و تگ را ذخیره کند.

۵. اعتبارسنجی و اتصال تگ‌ها هنگام ساخت مقاله

در فایل articles.service.ts، سرویس ساخت مقاله ابتدا تکراری نبودن آدرس مقاله را بررسی می‌کند؛ سپس تگ‌ها را اعتبارسنجی و بازیابی می‌کند.

حذف شناسه‌های تکراری

const tagIds = [...new Set(data.tagIds ?? [])];

اگر ورودی شامل [1, 1, 2] باشد، نتیجه [1, 2] خواهد بود.

بررسی معتبر بودن شناسه‌ها

if (
  tagIds.some(
    (id) => !Number.isInteger(id) || id < 1,
  )
) {
  throw new AppError("شناسه تگ معتبر نیست", 400);
}

این بررسی شناسه‌های نامعتبر مانند صفر، اعداد منفی و اعداد اعشاری را رد می‌کند.

پیداکردن تگ‌ها در دیتابیس

const tags = tagIds.length
  ? await tagRepository
      .createQueryBuilder("tag")
      .where("tag.id IN (:...tagIds)", { tagIds })
      .getMany()
  : [];

سپس تعداد تگ‌های پیدا‌شده با تعداد شناسه‌های درخواستی مقایسه می‌شود: 

if (tags.length !== tagIds.length) {
  throw new AppError("یک یا چند تگ پیدا نشد", 404);
}

ذخیره مقاله همراه تگ‌ها

const article = articleRepository.create({
  title: data.title,
  slug: data.slug,
  content: JSON.stringify(data.content),
  status: data.status ?? "draft",
  userId,
  tags,
});

return articleRepository.save(article);
نکته امنیتی: کلاینت نباید بتواند با ارسال یک شناسه ساختگی، رابطه‌ای با تگی ناموجود ایجاد کند. شناسه‌ها باید اعتبارسنجی شوند و وجود تمام تگ‌های انتخاب‌شده در دیتابیس بررسی شود.

۶. ویرایش تگ‌های مقاله

تابع updateArticle برای تغییر تگ‌ها اصلاح شد. همچنین فیلد tagIds به updateArticleSchema اضافه شد.

قانون مهم در ویرایش

if (data.tagIds !== undefined) {
  // اعتبارسنجی و بازیابی تگ‌های جدید
  // جایگزینی رابطه قبلی
}

بررسی !== undefined اهمیت زیادی دارد؛ چون نبودن فیلد و ارسال آرایه خالی دو معنای متفاوت دارند.

ورودی PATCH رفتار مورد انتظار
{"tagIds":[1]} تگ‌های مقاله با تگ شماره ۱ جایگزین می‌شوند.
{"tagIds":[1,2]} تگ‌های شماره ۱ و ۲ به مقاله متصل می‌شوند.
{"tagIds":[]} تمام ارتباط‌های تگ مقاله حذف می‌شوند.
{"status":"published"} تگ‌های قبلی دست‌نخورده می‌مانند.

جایگزینی تگ‌ها

article.tags = tags;

بعد از جایگزینی تگ‌ها، مقاله با استفاده از مخزن TypeORM ذخیره می‌شود: 

return articleRepository.save(article);

این کار به TypeORM اجازه می‌دهد تغییرات رابطه را در جدول واسط مدیریت کند.

توجه: پیش از استفاده از این کد، مطمئن شوید updateArticleSchema واقعاً فیلد tagIds را می‌پذیرد. اگر Zod آن را حذف کند، سرویس هیچ‌وقت تغییر تگ‌ها را دریافت نمی‌کند.

۷. خطای پیدا نشدن مقاله و بررسی مالکیت

هنگام ویرایش مقاله شماره ۱۳، پیام «مقاله پیدا نشد» دریافت شد. بخشی از علت، نحوه فراخوانی getArticleById بود.

تابع دریافت مقاله شرطی مشابه این داشت:

if (
  article.status !== "published" &&
  article.userId !== viewerUserId
) {
  throw new AppError("مقاله پیدا نشد", 404);
}

مقاله پیش‌نویس فقط در صورتی قابل مشاهده است که شناسه نویسنده با کاربر درخواست‌دهنده مطابقت داشته باشد.

در تابع ویرایش، ابتدا مقاله را بدون شناسه کاربر به getArticleById می‌دادیم؛ به همین دلیل مقاله پیش‌نویس ممکن بود پیدا نشود.

اصلاح اولیه

const article = await getArticleById(id, userId);

بعداً، به دلیل مشکل پردازش محتوای مقاله، نحوه دریافت مقاله در updateArticle تغییر کرد تا نسخه خام موجودیت از دیتابیس گرفته شود. 

const article = await articleRepository.findOne({
  where: { id },
  relations: {
    tags: true,
  },
});

if (!article) {
  throw new AppError("مقاله پیدا نشد", 404);
}

پس از آن، بررسی مالکیت باید حتماً باقی بماند: 

if (article.userId !== userId) {
  throw new AppError(
    "شما اجازه ویرایش این مقاله را ندارید",
    403,
  );
}
نکته امنیتی بسیار مهم: دریافت مستقیم مقاله از مخزن نباید باعث حذف کنترل دسترسی شود. هر کاربر باید فقط اجازه ویرایش مقاله‌ای را داشته باشد که مالک آن است، مگر اینکه سیاست مجوز دیگری به‌صورت آگاهانه پیاده‌سازی شده باشد.

۸. خطای JSON در محتوای مقاله

هنگام اجرای PATCH، خطای زیر در ترمینال ظاهر شد: 

SyntaxError: "[object Object]" is not valid JSON

ابتدا تابع parseArticleContent فقط انتظار رشته داشت و آن را با JSON.parse تبدیل می‌کرد. 

const parseArticleContent = (content: string) => {
  return JSON.parse(content);
};

بررسی خروجی ترمینال نشان داد: 

ARTICLE CONTENT: [object Object]
CONTENT TYPE: string

بنابراین مشکل فقط یک خطای TypeScript نبود. مقدار نامعتبر [object Object] واقعاً داخل ستون content مقاله شماره ۱۳ ذخیره شده بود.

چرا این اتفاق می‌افتد؟

اگر یک آبجکت جاوااسکریپت مستقیماً به رشته تبدیل شود، معمولاً نتیجه [object Object] خواهد بود. این مقدار JSON معتبر نیست.

برای تبدیل صحیح آبجکت به JSON از این روش استفاده می‌کنیم:

JSON.stringify(data.content)

و برای تبدیل رشته JSON به مقدار جاوااسکریپت:

JSON.parse(content)

بررسی نوع ستون دیتابیس

دستور زیر اجرا شد:

SHOW COLUMNS FROM articles LIKE 'content';

نوع ستون content برابر TEXT بود. این نوع ستون می‌تواند رشته JSON را ذخیره کند؛ پس برای این مشکل نیازی به تغییر نوع ستون نبود.

اصلاح محتوای خراب مقاله شماره ۱۳

چون محتوای اصلی مقاله در قالب معتبر ذخیره نشده بود، یک محتوای معتبر جایگزین شد. 

UPDATE articles
SET content = '[{"type":"paragraph","text":"بررسی اتصال مقاله به تگ"}]'
WHERE id = 13;

این دستور فقط محتوای مقاله با شناسه ۱۳ را تغییر داد. محتوای اصلی خراب‌شده از این رشته قابل بازیابی خودکار نبود.

در محیط واقعی، پیش از اجرای UPDATE مستقیم روی دیتابیس، از داده‌ها نسخه پشتیبان بگیرید. تغییر دستی محتوا فقط زمانی مناسب است که ساختار محتوای مورد انتظار را بشناسید.

۹. اصلاح parseArticleContent

برای جلوگیری از اجرای JSON.parse روی آبجکت، تابع به شکل زیر تغییر کرد: 

const parseArticleContent = (content: unknown) => {
  if (typeof content === "string") {
    try {
      return JSON.parse(content);
    } catch {
      throw new AppError(
        "ساختار محتوای مقاله معتبر نیست",
        500,
      );
    }
  }

  if (content !== null && typeof content === "object") {
    return content;
  }

  throw new AppError(
    "ساختار محتوای مقاله معتبر نیست",
    500,
  );
};

این تابع اگر رشته JSON دریافت کند، آن را تجزیه می‌کند و اگر از قبل یک آبجکت باشد، آن را بدون تجزیه دوباره برمی‌گرداند.

با این حال، این تابع به‌تنهایی محتوای خراب‌شده‌ای مثل [object Object] را بازیابی نمی‌کند. در آن وضعیت، باید داده اصلاح شود یا خطای کنترل‌شده برگردانده شود.

نکته: بررسی typeof content === "object" به‌تنهایی اعتبار ساختار مقاله را تضمین نمی‌کند. برای اعتبارسنجی کامل، باید شکل آرایه و نوع بلوک‌های محتوا هم بررسی شود.

۱۰. انتشار مقاله با PATCH

برای انتشار مقاله، مقدار وضعیت از draft به published تغییر داده می‌شود.

درخواست تست‌شده:

PATCH http://localhost:3100/api/v1/articles/13

بدنه درخواست:

{
  "status": "published"
}

مقادیر وضعیت در پروژه:

  • draft: مقاله پیش‌نویس است.
  • published: مقاله منتشر شده است.

در این پروژه، امکان انتشار از طریق ویرایش مقاله پیاده‌سازی شده و درخواست انتشار با موفقیت تست شد.

انتشار باید تابع قوانین مالکیت و مجوزهای برنامه باشد. همچنین برای نمایش عمومی مقاله‌ها، فیلتر وضعیت published باید در APIهای عمومی اعمال شود.

۱۱. تست اتصال تگ به مقاله

پس از اصلاح اسکیما و سرویس، درخواست ویرایش تگ‌ها برای مقاله شماره ۱۳ با موفقیت اجرا شد. 

PATCH http://localhost:3100/api/v1/articles/13

بدنه درخواست:

{
  "tagIds": [1]
}

نتیجه تست موفق بود و تگ مقاله با شناسه تگ شماره ۱ جایگزین شد. همچنین مشخص شد که تغییر وضعیت انتشار و تغییر تگ‌ها می‌توانند جداگانه انجام شوند.

تست مستقیم دیتابیس

برای بررسی ارتباط‌ها می‌توان از دستور زیر استفاده کرد: 

SELECT *
FROM article_tags
WHERE articlesId = 13;

اگر ارتباط ذخیره شده باشد، باید ردیفی با شناسه مقاله ۱۳ و شناسه تگ انتخاب‌شده مشاهده شود.

۱۲. پاک‌سازی کد و بررسی TypeScript

هنگام بررسی مشکل، یک دستور موقت برای چاپ شناسه تگ‌ها و تگ‌های پیدا‌شده اضافه شده بود: 

console.log("tagIds:", tagIds, "found tags:", tags);

بعد از موفقیت تست‌ها، این خط حذف شد تا خروجی ترمینال تمیز بماند.

سپس دستور زیر اجرا شد:

npm run typecheck
نتیجه: دستور بررسی TypeScript بدون خطا اجرا شد.

این دستور خطاهای نوعی TypeScript را بررسی می‌کند؛ اما به‌تنهایی تضمین نمی‌کند که تمام درخواست‌های API یا رفتارهای دیتابیس درست کار می‌کنند. تست‌های API همچنان ضروری هستند.

۱۳. راهنمای تست APIها

سرور توسعه از دستور زیر اجرا می‌شود: 

npm run dev

آدرس پایه API: 

http://localhost:3100/api/v1
عملیات روش مسیر هدف
دریافت مقاله GET /articles/13 بررسی اطلاعات مقاله
انتشار مقاله PATCH /articles/13 تغییر status به published
تغییر تگ مقاله PATCH /articles/13 جایگزینی تگ‌های مقاله
مشاهده تگ‌ها GET /tags دریافت فهرست تگ‌ها
دریافت تگ GET /tags/1 دریافت یک تگ

برای درخواست‌های محافظت‌شده، توکن ورود را در Postman از مسیر Authorization → Bearer Token وارد کنید.

شناسه مقاله ۱۳ در این مستند برای مثال استفاده شده است. شناسه‌ها به دیتابیس فعلی وابسته‌اند و ممکن است در محیط دیگری متفاوت باشند.

۱۴. نکات کلیدی که باید به خاطر بسپاریم

  • فیلدهای درخواست باید در اسکیماهای Zod تعریف شوند.
  • DTO به‌تنهایی ورودی HTTP را اعتبارسنجی نمی‌کند.
  • برای ذخیره آرایه یا آبجکت در ستون متنی از JSON.stringify استفاده می‌کنیم.
  • برای خواندن JSON معتبر از JSON.parse استفاده می‌کنیم.
  • رشته [object Object] محتوای JSON معتبر نیست.
  • پیش از ساخت رابطه، وجود تگ‌های انتخاب‌شده را بررسی می‌کنیم.
  • در PATCH، فیلد ارسال‌نشده با آرایه خالی یکسان نیست.
  • برای جایگزینی رابطه تگ‌ها، مقدار article.tags را تنظیم می‌کنیم.
  • در ویرایش مقاله باید مالکیت مقاله بررسی شود.
  • نمایش عمومی مقاله باید فقط وضعیت‌های مجاز را برگرداند.
  • خطاهای دیتابیس و API باید کنترل‌شده و قابل فهم باشند.
  • پس از هر تغییر مهم، هم typecheck و هم تست API انجام می‌دهیم.

۱۵. مرحله بعدی پروژه

مرحله بعد، اضافه‌کردن فیلتر مقالات بر اساس شناسه تگ است. هدف این است که کاربر بتواند مقاله‌های مرتبط با یک تگ را دریافت کند.

نمونه درخواست موردنظر

GET http://localhost:3100/api/v1/articles?tagId=1

این درخواست باید مقاله‌هایی را برگرداند که به تگ شماره ۱ متصل هستند؛ البته محدودیت‌های دسترسی و وضعیت انتشار باید همچنان رعایت شوند.
