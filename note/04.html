۱. معرفی پروژه

هدف، ساخت بک‌اند یک وب‌سایت مقاله است. بک‌اند مسئول دریافت درخواست‌ها، بررسی اطلاعات، ارتباط با دیتابیس و برگرداندن پاسخ مناسب به کلاینت است.

فناوری کاربرد
TypeScript نوشتن کد جاوااسکریپت همراه با بررسی نوع داده‌ها
Express ساخت API و مدیریت درخواست‌های HTTP
TypeORM ارتباط بین کد TypeScript و دیتابیس رابطه‌ای

مسئولیت هر لایه چیست؟

  • Middleware: قبل از اجرای کنترلر، کارهایی مثل احراز هویت را انجام می‌دهد.

۴. دیتابیس و Migration

برای اتصال پروژه به MariaDB یا MySQL از TypeORM استفاده شده است. تنظیمات اتصال در فایل data-source.ts قرار دارد و مقادیر اتصال از تنظیمات محیطی خوانده می‌شوند.

data-source.ts — نمونه تنظیمات اصلی
import "reflect-metadata";
import { DataSource } from "typeorm";

import { env } from "../../config/env";
import { User } from "../../modules/users/user.entity";
import { Article } from "../../modules/articles/article.entity";

export const AppDataSource = new DataSource({
  type: "mysql",
  host: env.DB_HOST,
  port: env.DB_PORT,
  username: env.DB_USER,
  password: env.DB_PASSWORD,
  database: env.DB_NAME,

  entities: [User, Article],

  migrations: [
    "articles-backend/src/database/migrations/*.ts",
  ],

  synchronize: false,
  logging: false,
});

مسیر دقیق Entityها باید با مسیر واقعی فایل‌های پروژه مطابقت داشته باشد. قطعه بالا برای توضیح تنظیمات است؛ آن را بدون بررسی مسیرهای فعلی جایگزین نکن.

چرا synchronize برابر false است؟

با synchronize: false، TypeORM به‌صورت خودکار ساختار جداول را تغییر نمی‌دهد. تغییرات ساختار دیتابیس با Migration انجام می‌شوند تا قابل پیگیری و کنترل باشند.

Migrationهای ثبت‌شده در پروژه

  • ساخت جدول کاربران (Users)
  • ساخت جدول مقالات (Articles)
  • افزودن فیلد هش رمز عبور به کاربران (passwordHash)
طبق گزارش مراحل قبلی، Migrationهای کاربران، مقالات و رمز عبور اجرا شده‌اند. پیش از اجرای مجدد هر Migration، وضعیت دیتابیس را بررسی کن.

۵. ثبت‌نام و ورود کاربر

سیستم احراز هویت دو عملیات اصلی دارد:

  • Register: ایجاد حساب کاربری و هش‌کردن رمز عبور.
  • Login: بررسی ایمیل و رمز عبور و تولید توکن دسترسی.

اعتبارسنجی اطلاعات ورود و ثبت‌نام

auth.validation.ts
import { z } from "zod";

export const registerSchema = z.object({
  name: z.string().trim().min(2).max(100),
  email: z.string().trim().email().max(150),
  password: z.string().min(8).max(72),
});

export const loginSchema = z.object({
  email: z.string().trim().email().max(150),
  password: z.string().min(1).max(72),
});

توضیح ساده کد

  • z.object() شکل داده مورد انتظار را تعریف می‌کند.
  • trim() فاصله‌های ابتدا و انتهای متن را حذف می‌کند.
  • min(2) حداقل طول را تعیین می‌کند.
  • max(100) حداکثر طول را تعیین می‌کند.
  • email() فرمت ایمیل را بررسی می‌کند.
محدودیت ۷۲ در این نمونه برای رمز عبور با توجه به محدودیت بایتی bcrypt در نظر گرفته شده است. بررسی بایتی نیز باید در سرویس انجام شود؛ طول کاراکترها همیشه با طول بایت یکسان نیست.

نمونه ثبت‌نام

در Postman درخواست زیر را بساز:

POST http://localhost:3100/api/v1/auth/register

بخش Body را روی JSON قرار بده:

{
  "name": "Ali Reza",
  "email": "ali@example.com",
  "password": "StrongPass123"
}

از ایمیلی استفاده کن که قبلاً در دیتابیس ثبت نشده باشد. پاسخ موفق معمولاً با وضعیت HTTP برابر 201 Created برمی‌گردد، اما ساختار دقیق پاسخ به کنترلر فعلی پروژه بستگی دارد.

نمونه ورود

POST http://localhost:3100/api/v1/auth/login
{
  "email": "ali@example.com",
  "password": "StrongPass123"
}

پس از ورود موفق، پاسخ باید توکن دسترسی را برگرداند. مقدار توکن را برای درخواست‌های محافظت‌شده استفاده کن و آن را در مکان عمومی منتشر نکن.

چرا رمز عبور را هش می‌کنیم؟

رمز عبور خام نباید مستقیماً در دیتابیس ذخیره شود. bcrypt رمز را هش می‌کند و هنگام ورود، رمز واردشده با هش ذخیره‌شده مقایسه می‌شود.

نمونه منطق bcrypt
const passwordHash = await bcrypt.hash(password, 12);

// هنگام ورود:
const isPasswordValid = await bcrypt.compare(
  password,
  user.passwordHash,
);
عدد ۱۲، تعداد دورهای هزینه bcrypt در این نمونه است. مقدار مناسب به توان پردازشی سرور و نیاز پروژه بستگی دارد.

۶. توکن JWT

پس از ورود موفق، سرور می‌تواند یک JWT صادر کند. کلاینت در درخواست‌های بعدی توکن را ارسال می‌کند تا سرور بتواند کاربر را شناسایی کند.

jwt.service.ts — نمونه منطق ثبت و بررسی توکن
import jwt from "jsonwebtoken";
import { env } from "../../config/env";

export interface JwtPayload {
  userId: number;
}

export function signAccessToken(userId: number): string {
  return jwt.sign(
    { userId },
    env.JWT_SECRET,
    {
      subject: String(userId),
      expiresIn: "1h",
    },
  );
}

export function verifyAccessToken(
  token: string,
): JwtPayload {
  const payload = jwt.verify(token, env.JWT_SECRET);

  if (
    typeof payload === "string" ||
    typeof payload.userId !== "number"
  ) {
    throw new Error("توکن نامعتبر است");
  }

  return {
    userId: payload.userId,
  };
}

معنی قسمت‌های مهم

  • userId: شناسه کاربری که توکن به او تعلق دارد.
  • JWT_SECRET: کلید محرمانه‌ای که برای امضا و بررسی توکن استفاده می‌شود.
  • expiresIn: "1h": توکن پس از یک ساعت منقضی می‌شود.
  • jwt.verify(): امضا و اعتبار توکن را بررسی می‌کند.
کلید JWT را داخل کد منتشرشده، Git یا پیام‌های عمومی قرار نده. مقدار آن باید از فایل محیطی امن خوانده شود. Payload توکن رمزگذاری‌شده نیست؛ اطلاعات حساس را داخل آن قرار نده.

۷. Middleware احراز هویت

Middleware تابعی است که قبل از رسیدن درخواست به کنترلر اجرا می‌شود. در این پروژه، Middleware توکن را از هدر درخواست می‌خواند و اعتبار آن را بررسی می‌کند.

common/middleware/auth.middleware.ts
import type {
  NextFunction,
  Request,
  Response,
} from "express";

import {
  verifyAccessToken,
} from "../../modules/auth/jwt.service";

export function authenticate(
  req: Request,
  res: Response,
  next: NextFunction,
) {
  const authorization = req.headers.authorization;

  if (!authorization?.startsWith("Bearer ")) {
    return res.status(401).json({
      success: false,
      message: "برای دسترسی به این منبع باید وارد شوید",
    });
  }

  const token = authorization
    .slice("Bearer ".length)
    .trim();

  if (!token) {
    return res.status(401).json({
      success: false,
      message: "توکن احراز هویت ارسال نشده است",
    });
  }

  try {
    const payload = verifyAccessToken(token);

    res.locals.userId = payload.userId;

    return next();
  } catch {
    return res.status(401).json({
      success: false,
      message: "توکن نامعتبر یا منقضی شده است",
    });
  }
}

هدر Authorization چیست؟

در Postman یا کلاینت، توکن به این شکل ارسال می‌شود:

Authorization: Bearer YOUR_ACCESS_TOKEN

عبارت Bearer نوع شیوه ارسال توکن را مشخص می‌کند. Middleware بعد از بررسی موفق، شناسه کاربر را در res.locals.userId قرار می‌دهد.

از این پس، شناسه مالک مقاله باید از اطلاعات کاربر احراز هویت‌شده گرفته شود، نه از مقداری که کلاینت آزادانه در Body ارسال می‌کند.

۸. ایجاد مقاله

اطلاعات مقاله می‌تواند شامل عنوان، آدرس یکتا، محتوا و وضعیت انتشار باشد. شناسه نویسنده از توکن کاربر دریافت می‌شود.

DTO چیست؟

DTO مخفف Data Transfer Object است. این ساختار مشخص می‌کند چه اطلاعاتی برای یک عملیات به سرویس ارسال می‌شوند.

articles.dto.ts — نمونه DTO
export interface CreateArticleDto {
  title: string;
  slug: string;
  content: string;
  status?: "draft" | "published";
}
در طراحی فعلی، userId نباید بخشی از اطلاعات قابل‌اعتماد ارسال‌شده توسط کاربر باشد. بنابراین در DTO ایجاد مقاله نباید userId را از Body دریافت کنیم؛ شناسه مالک را از توکن می‌گیریم.

سرویس ایجاد مقاله

articles.service.ts — نمونه منطق ایجاد
import { articleRepository } from "./articles.repository";
import type { CreateArticleDto } from "./articles.dto";
import { AppError } from "../../common/errors/app.error";

export const createArticle = async (
  data: CreateArticleDto,
  userId: number,
) => {
  const existingArticle = await articleRepository.findOneBy({
    slug: data.slug,
  });

  if (existingArticle) {
    throw new AppError(
      "این آدرس مقاله قبلاً ثبت شده است",
      409,
    );
  }

  const article = articleRepository.create({
    title: data.title,
    slug: data.slug,
    content: data.content,
    status: data.status ?? "draft",
    userId,
  });

  return articleRepository.save(article);
};

توضیح خط‌به‌خط منطق

  1. سرویس اطلاعات مقاله و شناسه کاربر را دریافت می‌کند.
  2. بررسی می‌کند آیا مقاله‌ای با همین slug وجود دارد یا خیر.
  3. اگر آدرس تکراری باشد، خطای 409 Conflict ایجاد می‌شود.
  4. اگر وضعیت ارسال نشده باشد، مقدار پیش‌فرض draft انتخاب می‌شود.
  5. مقاله همراه با شناسه مالک در دیتابیس ذخیره می‌شود.

درخواست ایجاد مقاله

POST http://localhost:3100/api/v1/articles

در Postman بخش Authorization را روی Bearer Token بگذار و توکن ورود را وارد کن.

{
  "title": "آموزش TypeScript",
  "slug": "typescript-guide",

توجه: در Body بالا عمداً userId وجود ندارد؛ مالکیت از اطلاعات احراز هویت‌شده استخراج می‌شود.

۹. مالکیت مقاله و جلوگیری از ویرایش غیرمجاز

فقط ورود کاربر کافی نیست. اگر کاربر وارد حساب خودش شده باشد، نباید بتواند مقاله متعلق به کاربر دیگری را ویرایش یا حذف کند.

الگوی بررسی مالکیت در سرویس

نمونه آموزشی برای updateArticle
export const updateArticle = async (
  id: number,
  data: Partial<CreateArticleDto>,
  userId: number,
) => {
  const article = await getArticleById(id);

  if (article.userId !== userId) {
    throw new AppError(
      "شما اجازه ویرایش این مقاله را ندارید",
      403,
    );
  }

  if (data.slug && data.slug !== article.slug) {
    const existingArticle =
      await articleRepository.findOneBy({
        slug: data.slug,
      });

    if (existingArticle) {
      throw new AppError(
        "این آدرس مقاله قبلاً ثبت شده است",
        409,
      );
    }
  }

  articleRepository.merge(article, {
    title: data.title,
    slug: data.slug,
    content: data.content,
    status: data.status,
  });

  return articleRepository.save(article);
};

الگوی بررسی مالکیت در حذف

نمونه آموزشی برای deleteArticle
export const deleteArticle = async (
  id: number,
  userId: number,
) => {
  const article = await getArticleById(id);

  if (article.userId !== userId) {
    throw new AppError(
      "شما اجازه حذف این مقاله را ندارید",

این دو قطعه، الگوی پیشنهادی بررسی مالکیت هستند؛ قبل از جایگزینی، آن‌ها را با نسخه نهایی سرویس خودت مقایسه کن. نتیجه نهایی باید این باشد که سرویس برای ویرایش و حذف، هم شناسه مقاله و هم شناسه کاربر احراز هویت‌شده را بررسی کند.

تفاوت وضعیت‌های HTTP

کد معنی
400 درخواست یا اطلاعات ورودی نامعتبر است.
401 کاربر احراز هویت نشده یا توکن معتبر نیست.
403 کاربر احراز هویت شده، اما اجازه انجام عملیات را ندارد.
404 مقاله یا منبع موردنظر پیدا نشده است.
409 تعارضی مثل تکراری‌بودن آدرس مقاله وجود دارد.
500 خطای پیش‌بینی‌نشده در سمت سرور رخ داده است.

۱۰. دریافت، جست‌وجو، فیلتر و صفحه‌بندی مقالات

در این بخش، API فهرست مقالات پارامترهایی برای صفحه، تعداد نتیجه‌ها، وضعیت انتشار و جست‌وجو در عنوان دریافت می‌کند.

articles.service.ts — نمونه getAllArticles
export const getAllArticles = async (
  page = 1,
  limit = 10,
  status?: "draft" | "published",
  search?: string,
) => {
  const safePage = Math.max(1, Math.floor(page));

  const safeLimit = Math.min(
    50,
    Math.max(1, Math.floor(limit)),
  );

  const query = articleRepository
    .createQueryBuilder("article")
    .orderBy("article.createdAt", "DESC")
    .skip((safePage - 1) * safeLimit)
    .take(safeLimit);

  if (status) {
    query.andWhere(
      "article.status = :status",
      { status },
    );
  }

  if (search?.trim()) {
    query.andWhere(
      "article.title LIKE :search",
      { search: `%${search.trim()}%` },
    );
  }

  const [articles, total] =
    await query.getManyAndCount();

  return {
    data: articles,
    pagination: {
      page: safePage,
      limit: safeLimit,
      total,
      totalPages: Math.ceil(total / safeLimit),
    },
  };
};

توضیح پارامترها

  • page: شماره صفحه موردنظر.
  • limit: تعداد مقالات در هر صفحه.
  • status: فیلتر بر اساس draft یا published.
  • search: جست‌وجو در عنوان مقاله.
  • skip(): تعداد رکوردهایی که باید از ابتدای نتایج رد شوند.
  • take(): حداکثر تعداد رکوردهای دریافت‌شده.
  • getManyAndCount(): دریافت نتایج و تعداد کل رکوردهای منطبق.

مثال صفحه‌بندی

GET http://localhost:3100/api/v1/articles?page=2&limit=10

این درخواست صفحه دوم را با حداکثر ۱۰ مقاله درخواست می‌کند. مقدار skip برابر ۱۰ خواهد بود.

مثال جست‌وجو و فیلتر هم‌زمان

GET http://localhost:3100/api/v1/articles?page=2&limit=10&search=typescript&status=published

این درخواست به دنبال مقالات منتشرشده‌ای می‌گردد که عنوانشان شامل عبارت TypeScript باشد.

جست‌وجوی نمونه با LIKE انجام می‌شود. رفتار حساس‌بودن به حروف بزرگ و کوچک به Collation دیتابیس بستگی دارد. برای جست‌وجوی پیشرفته‌تر می‌توان بعداً از Full-Text Search استفاده کرد.

دریافت یک مقاله با شناسه

نمونه getArticleById
export const getArticleById = async (
  id: number,

    throw new AppError(

۱۱. مسیرهای API

مسیرهای زیر بر اساس ساختار اخیر پروژه مستند شده‌اند. آدرس پایه API برابر http://localhost:3100/api/v1 است.

متد مسیر کاربرد احراز هویت
POST /auth/register ثبت‌نام کاربر خیر
POST /auth/login ورود کاربر خیر
GET /articles فهرست، جست‌وجو و فیلتر مقالات در ساختار اخیر عمومی
GET /articles/:id دریافت یک مقاله در ساختار اخیر عمومی
POST /articles ایجاد مقاله بله
PATCH /articles/:id ویرایش بخشی از مقاله بله
DELETE /articles/:id حذف مقاله بله

نمونه فایل Route مقالات

articles.routes.ts
import { Router } from "express";

import {
  authenticate,
} from "../../common/middleware/auth.middleware";

import {
  createArticleController,
  deleteArticleController,
  getAllArticlesController,
  getArticleByIdController,
  updateArticleController,
} from "./articles.controller";

const router = Router();

// Public routes
router.get("/", getAllArticlesController);
router.get("/:id", getArticleByIdController);

// Protected routes
router.post(
  "/",
  authenticate,
  createArticleController,
);

router.patch(
  "/:id",
  authenticate,
  updateArticleController,
);

router.delete(
  "/:id",
  authenticate,
  deleteArticleController,
);

export default router;
اگر مقاله‌های پیش‌نویس خصوصی هستند، عمومی‌بودن GETها به‌تنهایی کافی نیست. سرویس فهرست و دریافت مقاله باید دسترسی به پیش‌نویس‌ها را نیز کنترل کند؛ در غیر این صورت ممکن است محتوای منتشرنشده به کاربران نمایش داده شود.

۱۲. راهنمای تست API با Postman یا Thunder Client

مرحله اول: ثبت‌نام

  1. درخواست جدید بساز.
  2. متد را روی POST قرار بده.
  3. آدرس http://localhost:3100/api/v1/auth/register را وارد کن.
  4. در بخش Body، گزینه raw و سپس JSON را انتخاب کن.
  5. اطلاعات نام، ایمیل و رمز عبور را ارسال کن.

مرحله دوم: ورود

  1. درخواست POST /api/v1/auth/login را ارسال کن.
  2. ایمیل و رمز عبور ثبت‌شده را وارد کن.
  3. توکن دسترسی موجود در پاسخ را کپی کن.

مرحله سوم: ایجاد مقاله

  1. درخواست POST /api/v1/articles بساز.
  2. در بخش Authorization، نوع Bearer Token را انتخاب کن.
  3. توکن مرحله قبل را وارد کن.
  4. عنوان، آدرس، محتوا و وضعیت مقاله را در Body ارسال کن.
  5. فیلد userId را از Body حذف کن.

مرحله چهارم: فهرست و جست‌وجو

GET http://localhost:3100/api/v1/articles

برای تست جست‌وجو و صفحه‌بندی:

GET http://localhost:3100/api/v1/articles?page=1&limit=10&search=typescript

مرحله پنجم: ویرایش مقاله

PATCH http://localhost:3100/api/v1/articles/1

نمونه Body:

{
  "title": "عنوان جدید مقاله"
}

توکن معتبر را در Authorization ارسال کن. شناسه ۱ باید متعلق به مقاله‌ای باشد که کاربر فعلی اجازه ویرایش آن را دارد.

مرحله ششم: حذف مقاله

DELETE http://localhost:3100/api/v1/articles/1

حذف را فقط روی مقاله آزمایشی انجام بده. انتظار می‌رود کاربر نتواند مقاله متعلق به کاربر دیگری را حذف کند.

آزمون‌های مهم احراز هویت و مالکیت

  • ایجاد مقاله بدون توکن باید رد شود.
  • ارسال توکن نامعتبر باید پاسخ 401 ایجاد کند.
  • ایجاد مقاله با توکن معتبر باید شناسه مالک را از توکن بگیرد.
  • ویرایش مقاله متعلق به کاربر دیگر باید رد شود.
  • حذف مقاله متعلق به کاربر دیگر باید رد شود.
  • جست‌وجو و فیلتر باید نتایج مورد انتظار را برگردانند.
  • شناسه مقاله ناموجود باید به پاسخ مناسب مانند 404 منجر شود.

۱۳. خطاهای اخیر و مفهوم آن‌ها

خطای TypeScript: ویژگی userId وجود ندارد

Property 'userId' does not exist on type 'CreateArticleDto'

علت: کد تلاش می‌کرد data.userId را بخواند، درحالی‌که userId از DTO حذف شده بود.

راه‌حل طراحی: شناسه کاربر را به‌عنوان آرگومان جداگانه از کنترلر به سرویس ارسال کن؛ این شناسه باید از Middleware احراز هویت گرفته شود.

خطای تعداد آرگومان‌ها

Expected 2 arguments, but got 1

علت: امضای تابع سرویس تغییر کرده بود، اما کنترلر هنوز تابع را با تعداد آرگومان قبلی صدا می‌زد.

راه‌حل: تعریف تابع سرویس و نحوه فراخوانی آن در کنترلر باید هماهنگ باشند. برای مثال، اگر سرویس به data و userId نیاز دارد، کنترلر باید هر دو را ارسال کند.

خطای Zod درباره userId

userId expected number, received undefined

علت: Schema هنوز وجود userId در Body را اجباری می‌دانست، درحالی‌که طراحی به استفاده از شناسه استخراج‌شده از توکن تغییر کرده بود.

راه‌حل: userId را از Schema ورودی ایجاد مقاله حذف کن و در کنترلر شناسه معتبر موجود در res.locals.userId را به سرویس بده.

خطای bcrypt

Error: data and hash arguments required

این خطا هنگام اجرای bcrypt.compare() نشان می‌دهد که رمز ورودی یا هش ذخیره‌شده به تابع نرسیده است.

مواردی که باید بررسی شوند:

  • آیا کاربر با ایمیل موردنظر در دیتابیس وجود دارد؟
  • آیا فیلد passwordHash از دیتابیس دریافت شده است؟
  • اگر فیلد در Entity با select: false تعریف شده، آیا در Query با addSelect() دریافت می‌شود؟
  • آیا مقدار صحیح به bcrypt.compare(password, passwordHash) ارسال می‌شود؟
نمونه دریافت هش در Query Builder
const user = await userRepository
  .createQueryBuilder("user")
  .addSelect("user.passwordHash")
  .where("user.email = :email", { email })
  .getOne();
در آخرین گزارش، کاربر اعلام کرده بود مشکل ناشی از اشتباه خودش بوده و اصلاح شده است. این بخش برای یادآوری روش عیب‌یابی نگه داشته شده است.

۱۴. نکات امنیتی مهم

  • رمز عبور را به‌صورت متن ساده در دیتابیس ذخیره نکن.
  • کلید JWT را در فایل محیطی نگه دار و آن را منتشر نکن.
  • در عملیات ایجاد مقاله، مالک را از توکن معتبر استخراج کن.
  • برای ویرایش و حذف مقاله، مالکیت را در سمت سرور بررسی کن.
  • ورودی‌های کاربر را با Zod یا اعتبارسنجی مناسب بررسی کن.
  • برای شناسه‌ها، مقادیر عددی مثبت و معتبر را بررسی کن.
  • برای خطاهای مورد انتظار از کدهای HTTP مناسب استفاده کن.
  • برای Queryهای دیتابیس از پارامترهای امن استفاده کن.
  • برای فهرست مقالات، سقف مشخصی برای limit قرار بده.
  • اطلاعات حساس مانند هش رمز عبور را در پاسخ API برنگردان.
  • اگر پیش‌نویس خصوصی است، دسترسی عمومی به آن را محدود کن.
  • برای تولید واقعی، محدودیت تعداد درخواست‌ها و مدیریت امن خطاها را نیز بررسی کن.
احراز هویت و مجوز دسترسی دو موضوع جدا هستند. JWT معتبر مشخص می‌کند درخواست از طرف چه کاربری آمده است؛ اما به‌تنهایی ثابت نمی‌کند آن کاربر اجازه ویرایش هر مقاله‌ای را دارد.

۱۵. چک‌لیست وضعیت پروژه

بر اساس آخرین گزارش‌های موجود از کارهای انجام‌شده:

  • ساخت بک‌اند با TypeScript و Express
  • تنظیم اتصال TypeORM به MariaDB / MySQL
  • ساخت جدول کاربران با Migration
  • ساخت جدول مقالات با Migration
  • افزودن فیلد هش رمز عبور به کاربران
  • تعریف مسیرهای ثبت‌نام و ورود
  • هش‌کردن رمز عبور با bcrypt
  • صدور و بررسی JWT
  • ساخت Middleware احراز هویت
  • محافظت از مسیرهای ایجاد، ویرایش و حذف مقاله
  • انتقال شناسه مالک مقاله از Body به اطلاعات احراز هویت‌شده
  • تغییر امضای سرویس‌ها برای دریافت شناسه کاربر
  • پیاده‌سازی یا تکمیل فهرست، جست‌وجو و صفحه‌بندی مقالات
  • بررسی وضعیت مقاله و جلوگیری از آدرس تکراری
  • اجرای typecheck و تست درخواست‌ها طبق گزارش کاربر
این چک‌لیست بر اساس اطلاعاتی است که در گفتگو گزارش شده‌اند و جایگزین بررسی مستقیم فایل‌های فعلی یا اجرای تست خودکار نیست.

موضوعاتی که در ادامه باید بررسی شوند

  1. تست نهایی جست‌وجو و فیلتر مقالات با داده‌های مختلف.
  2. اطمینان از محدودیت مالکیت در ویرایش و حذف مقاله.
  3. اطمینان از اینکه پیش‌نویس‌های خصوصی به کاربران عمومی نمایش داده نمی‌شوند.
  4. تست خطاهای ورودی نامعتبر، توکن منقضی و مقاله ناموجود.
  5. بررسی مدیریت خطاها و اعتبارسنجی همه ورودی‌های API.
  6. پس از تأیید این موارد، ادامه توسعه امکانات مقاله.
